## Agreed product direction

HardHit's main mode remains the six-hitting contest: six legal deliveries per side, biggest six wins, and a wicket does not end a regular innings. Make the underlying ball, contact, decisions and controls more credible while retaining those explicit contest rules. Do not silently replace them with conventional team innings or add a separate mode as a prerequisite.

**Core requirement:** realistic cricket logic and physics are the default for the whole game, not an optional feature or mode. Do not trade correctness of the underlying decisions or physics for device performance or a simplified scoring model. Where evidence is missing, make the uncertainty and remaining acceptance gate explicit rather than calling an approximation realistic. Graphics quality and rendering effects should adapt to device capability while preserving the same gameplay simulation and decisions.

- Aim for broad web-device support, prioritizing Android and iPhone optimization and testing first, while maintaining desktop keyboard and browser support.
- Assistance is an on/off setting whose strength depends on the main player's level. Its level mapping, progression and exact effects still need to be designed and tested. It may help the player understand or execute controls, but must not change the underlying physics, laws, scoring or event results for the same executed inputs. Disclose any transformation from intended input to executed input and make unassisted behavior measurable.
- Ask new players during setup whether to enable assistance. Main-player level should reflect both match experience and batting and bowling performance; the exact formula remains to be designed. Level should also improve batter and bowler attributes within bounded, realistic ranges, independently of assistance. Save progression on the device across offline matches. Attribute improvements represent the player's capabilities within the same underlying simulation, not a separate physics or scoring model.
- For development and testing, provide a player-level picker dropdown so reviewers can try different main-player levels without earning them. The assistance curve (including whether strength increases or decreases with level) remains undecided; the picker chooses a test player level, not a committed assistance policy. Test overrides must be clearly labeled, isolated from saved progression and unavailable in normal release play unless deliberately enabled for development.
- Introduce automatic fielders and running first, then offer players both automatic running and a choice to run. In manual running, a poor decision can result in a run-out, determined by ball, fielder and crease timing. Plan manual fielding separately if later desired.
- For phone batting, let the player select shot and direction, then time the swing.
- Improve the offline AI first. Online matches are a later, separately scoped decision, not a dependency for offline improvements.
- Keep the current longest-six winner and tie-break rules; a wicket does not end the innings before all six legal balls are completed. Preserve existing saved data and distinguish a playability approximation from a calibrated measurement. Camera batting remains outside this plan.
- Follow applicable ICC playing conditions and MCC Laws for cricket rules except explicit contest overrides. Law 19 defines a boundary six but does not specify a longest-six ranking metric. The agreed contest metric is horizontal carry from the bat–ball contact point to the first landing point, excluding bounce and roll; when a stand or roof interrupts flight, project the uninterrupted landing point. Compare unrounded simulated distances for ranking even when displayed rounded values match, then use the existing tie-breaks if distances are equal. This is a contest rule, not a claim about an ICC distance convention.

## What works well

- Match and practice share important batting resolution and delivery trajectory functions, reducing—but not eliminating—the risk of visual and scoring disagreement.
- The shot flight uses fixed simulation steps; unit cases cover frame-rate damping, bounce and boundary ordering. The rendered pitch, stumps and ball have explicit measured dimensions.
- Extras, free hits, simplified LBW/bowled and innings transitions have meaningful representative unit tests. Practice has isolated progression and supports batting and bowling configurations.
- Keyboard, touch, handedness, pause/rotation, interrupted inputs and callbacks have automated regression coverage. Local storage handles unavailable or malformed data without preventing a match.
- There is a documented physics evidence trail and an explicit description of the contest's nonstandard rules. The code has browser regression scripts and a reproducible production build.

First demonstrate a deterministic six through the full input-to-score path and a negative control; keep the strict assertion. Define exactly when an outcome is provisional/final, isolate each delivery by generation, and make resolution idempotent. Automated: seeded full matches in both orders, strict six, duplicate/stale callback and pause/rematch race cases, fixed-seed replays at multiple frame rates. Acceptance: a missed swing cannot create a clean hit; center/off-center/edge cases show consistent contact and motion; equivalent mirrored inputs behave symmetrically; held-out measured launch conditions meet predeclared tolerances. **Phase 5 — Flight, surface and stadium.** Replace fixed assumptions only with calibrated, bounded drag/bounce/rolling behavior, optional spin/lift and ground properties supported by evidence.
